# M5 多 Pass Graph cohort、Runtime 时序与持久化边界

M5 把 pass-local Graph 与项目级 PassGraph 拆开，以 resolved channel environment 编译 Graph，并把所有启用的 Graph pass 作为单一 Runtime cohort 接受。候选 artifact 不会进入 `effectiveSources`，PassGraph/Code/Graph 语义变化也会在导出票据路径上失效旧状态。主要阻塞集中在恢复和 authoring 转换：带 `iChannel Sample` 的已保存 Graph 会因恢复分类遗漏 environment 而降级只读，旧 M3 Graph channels 也迁移成 resolver 拒绝的 endpoint。验证脚本、类型检查、构建和 Rust 测试均通过，但未覆盖这些 App/UI 调用链或真实 `bindChannels` 索引选择。

Watch for: **confirmed** — 已保存的 channel-sample Graph 无法以可编辑状态重开；**confirmed** — 旧 M3 Graph authoring + legacy buffer channels 打开后 PassGraph 必然无效；**confirmed** — 新建 Code 连接及 Graph/Code 切换会制造 resolver 拒绝且只能删边重建的 endpoint；**confirmed** — 打开与 autosave 恢复不核对 PassGraph reference revision/formatVersion；**confirmed** — M5 Runtime 验证只测纯规划结果，未执行 WebGL texture index/flip 路径。

**Verdict**: NEEDS_CHANGES

## High-level view

Graph cohort 接受边界是 all-or-nothing：所有启用 Graph pass 的 candidate 先组成一次 Runtime setup，成功后才统一写入 accepted artifact。Graph 编辑通过 stale 状态阻断 ticket，Code/PassGraph 编辑立即推进 Runtime revision，`effectiveSources` 只读取 accepted artifact。

Runtime 按 resolved DAG 执行 buffer，统一 flip 后再执行 Image；current/previous 的实现索引与这一时序一致。风险在于纯 planner 测试与 WebGL executor 是两套逻辑，现有验证无法捕获 `bindChannels`、flip、preview/capture 之间的实现漂移。

保存会按当前 PassGraph environment 重编译 Graph、核对 accepted artifact，并把 meta 作为原子批次的最终提交标记。打开虽先做 environment-aware 检查，App 激活时却再次无 environment 编译，合法 channel-sample Graph 因而被降级为只读恢复。

旧 channels 投影已保留非 buffer 数据并对不可表示 feedback fail closed，但 Graph-authored target 仍收到只允许 Code 使用的 `code-slot`。PassGraph UI 与 authoring 切换也没有把 endpoint kind、slot 和目标 authoring 作为原子状态转换。

## Persisted channel-sample Graph 在激活阶段丢失 resolved environment

`openProjectFrom` 把 `channelEnvironment[pass]` 与 resolved revision 传给 `inspectPersistedGraph`，但 `App.activatePersistedGraph` 随后调用 `classifyPersistedGraph(document)`；`src/state/graphRecovery.ts` 的该函数只执行无 options 的 `compileGraph(document)`。本次复现中，同一 `input.channel-sample` 文档无 environment 得到 `ok: false`/`compiler.internal`，传入 `{ sample: 0 }` 后成功。

这是 **confirmed** 的主路径故障：保存合法 channel-sample 项目并重开，`activatePersistedGraph` 会进入 `readonly-recovery`，不创建 editor，也不发起正常 cohort 编译。用户只能保留 generated fallback 或转为 Code。`classifyPersistedGraph` 应接收 `CompileGraphOptions`，并使用当前 resolved environment/revision；也可直接复用 open 阶段已完成的 classification，避免同一文档按两套环境判定。

## 旧 M3 Graph channels 被迁成当前契约禁止的 endpoint

`passGraphFromLegacy`（`src/project/passGraph.ts`）把所有 legacy buffer channel 投影为 `endpoint: { kind: 'code-slot' }`，未按 target authoring 分支；`resolvePassGraph` 则拒绝 Graph target 上的 code-slot。复现一个无 PassGraph 引用、Image 为 Graph authoring、Image channel0 指向 Buffer A 的 M3 项目，resolution 返回 `ok: false` 和 `pass-graph.endpoint-authoring`，这是 **confirmed** 的兼容性阻塞。

Graph 随后无法进入 Runtime cohort，保存也被拒绝；删除旧边虽然能恢复项目，却会丢掉 channel 配置。迁移需要读取 Graph 文档并建立稳定 endpoint，或引入明确的 migration-only slot endpoint；无法自动无损映射时，应提供可操作的转换界面。

## PassGraph 面板与 authoring 切换不能原子转换 endpoint

`ProjectPassGraphPanel.addEdge` 对默认 Code Image 创建 `code-slot`，却无条件设置 `slot: { mode: 'auto' }`；resolver 要求 Code endpoint 使用同号 manual slot。这是 **confirmed** 的 UI 自产无效状态：启用任意 Buffer 后点击“新增连接”，项目立即停止编译/保存。slot 下拉此时被禁用，若目标是 iChannel0，必须先改到别的 endpoint 再改回来。

`App.createPassGraphEditor` 和 `detachPassGraph` 只修改 authoring/editor/source，不转换该 target 的 PassGraph endpoint。面板 `onChange` 又按旧 `item.endpoint.kind` 分支，而不是目标当前 authoring：Graph→Code 后选 `iChannelN` 仍写 graph-channel，Code→Graph 后节点 ID 被 `Number(...)` 转成无效 slot。这是 **confirmed** 的不可原位修复状态，只能删边重建。

Code 新边应直接使用同号 manual slot。Detach 可用当前 resolved slot 生成 code-slot/manual；创建 Graph 时应为既有连接建立 channel-sample endpoint，或在转换前阻止并明确要求处理连接。endpoint 选择器必须按 target authoring 构造新的 union 分支。

## PassGraph reference identity 未参与打开与 autosave 恢复验证

`saveProjectTo` 写入 `passGraph.formatVersion = CURRENT_PASS_GRAPH_VERSION` 和 resolved `revision`，但 `openProjectFrom` 只使用 reference file；代码库没有读取 `meta.passGraph.revision`，也没有比较 reference `formatVersion` 与实际文档版本。因此这是 **confirmed** 的完整性缺口：保留旧 meta、修改 PassGraph 的 timing/filter/wrap 后，项目静默采用新拓扑；reference 声明未来版本而文件伪装为 v1 时也不会 fail closed。

Autosave 同时保存当前 PassGraph 与可能仍含上次保存 revision 的 meta，恢复时不重建或检查 identity。timing/filter/wrap 和纯 Code 项目不会改变 generated source，fallback hash 无法代替 PassGraph revision。open 应把 version/revision 不一致视为 error 或显式 recovery；autosave 应记录当前 resolved revision，无效文档则记录 stale/invalid 状态。

## Runtime timing 的实现不变量缺少 executor 级回归

这是 **confirmed** 的测试缺口：`verify-m5.mjs` 只断言一个 previous buffer 输入和一个 current Image 输入的 `planRuntimeFrame` 标签，没有执行 private `bindChannels`、多 Buffer current DAG、Image previous、统一 flip、preview target 或 capture 恢复。纯 planner 与 WebGL executor 使用独立逻辑，前者通过不能证明后者正确。应提取 `phase + timing + readIndex` 到共享纯函数并覆盖 flip 前后矩阵，再增加 fake-WebGL 或浏览器集成用例验证 preview/capture 不改变反馈历史和目标尺寸。
