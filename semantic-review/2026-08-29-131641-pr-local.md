# Visual/Sound 分域调度复审与剩余竞态

本轮逐项复核了上一报告的五个问题。禁用 Graph 门禁、stale-ticket 失败语义和 Sound snapshot 生命周期证明已经补齐，Visual/Sound ticket 也已改用各自的 setup revision。常规跨域 debounce 会合并请求，successful revision 与 Visual Graph cohort 接受仍保持 fail-closed；但一个未登记的即时 Graph 回调仍可能吞掉新请求，Sound-only 编译还会丢弃归因到 Common 的错误。两项都会让当前域停在错误的 UI/调度状态，因此本轮不能批准。

Watch for: **confirmed** — stale 的 Graph 创建回调会在检查 revision 前清空共享 pending domains；**confirmed** — Sound-only candidate 的 Common 源码错误不会进入 Sound diagnostics，状态栏可显示“编译通过”。

**Verdict**: NEEDS_CHANGES

## High-level view

Visual 与 Sound 现在各自维护 setup revision、successful revision 和 code-lane status；ticket 只冻结格式实际需要的 lane。普通 Visual/Sound 快速编辑通过 pending-domain 并集合并，但 Graph 创建使用未保存句柄的 0ms 回调，而且该回调先消费集合再拒绝 stale revision，给新请求留下丢失窗口。

Runtime-facing Graph 聚合已收窄到启用 pass：accepted uniforms、candidate artifacts、eligibility artifacts 和阻断诊断不再让禁用 Buffer/Sound Graph 污染活动域。禁用 Graph 的 authoring 文档与保存检查仍保留，不再承担 Runtime acceptance 门禁。

导出对 stale ticket 的处理已经从用户取消分离。状态栏的 pass/domain 选择也已分离，但 Sound lane 只接收 `sound` origin；Runtime 对共享源码报错使用 `common` origin，导致 Sound-only 失败没有可见错误。

M6 verifier 现在固定检查 Sound sampler，并在 `renderAudio` yield 期间替换 snapshot，证明旧 program/texture 在消费者结束前保留、结束后释放。accepted Graph cohort 和 successful revision 只在对应 Runtime 域成功后推进。

## 分域 ticket 与 debounce 合并中的 stale-consume 窗口

`reserveRuntimeSetupRevision` 只推进请求涉及的 lane revision/status，并把 domain 并入 `pendingCompileDomains`。Visual-only 与 Sound-only ticket 分别绑定各自 revision，`verify-m6` 也覆盖了非依赖 lane 变化不会使票据失效（`src/App.tsx:553-605`、`src/export/exportEligibility.ts:57-111`、`scripts/verify-m6.mjs:517-558`）。常规 `scheduleCompile` 与 `scheduleGraphCompile` 会互相取消旧 timer，由后发回调消费合并集合。

**confirmed** — Graph 创建路径没有保存 0ms timer，并在调用 `compileGraphCohort` 前求值 `consumePendingCompileDomains()`（`src/App.tsx:953-955`）。如果它预约 revision 1 后另一个域先预约 revision 2，旧回调会取走 `{ visual: true, sound: true }`，再因 revision 1 stale 而返回；revision 2 的 timer 随后只能取得空集合。`scheduleCompile` 也在 freshness check 前消费集合（`src/App.tsx:1017-1019`）。

```text
创建 Visual Graph       reserve r1, pending = V
Sound 编辑              reserve r2, pending = V|S
未登记的 r1 回调        consume V|S -> stale -> return
r2 debounce 回调        consume ∅ -> 不请求任何 Runtime 域
结果                     两个 lane 保持 pending，直到下一次编辑
```

消费动作应发生在确认回调仍拥有当前 revision 之后，或改为按 revision 归属并由唯一 scheduler 原子接管 pending domains。还需增加 coordinator 测试，覆盖 Graph 立即编译与另一域 debounce 的两种先后顺序。

## 禁用 Graph 从 Runtime 聚合中退出

纹理 issues 仅在 `runtimePassEnabled(pass)` 时进入门禁，accepted Graph uniforms 使用同一过滤，candidate setup 跳过禁用 pass，导出 artifacts 与 Graph cohort 从 `enabledGraphPasses()` 开始（`src/App.tsx:417-431,465-501,553-600,695-718`）。上一报告中禁用 Graph 的 missing texture 或 accepted uniform 阻断活动域的路径已关闭；禁用文档的 compiler diagnostics 只留在完整 Diagnostics Pane 与保存检查。

## Stale ticket 现在是导出失败

`ExportDialog` 单独记录 `ticketFailureReason`。batch 失效走错误态，最终写入前失效则抛出实际原因，PNG、GIF、MP4、WebM 与 WAV 不再把内容变化报告成用户取消（`src/components/ExportDialog.tsx:188-210,223-358`）。

## Sound-only Common 错误绕过活动域状态栏

`activeCompileStatus` 已选择 Visual/Sound code lane 或活动 Graph status，`activeDiagnosticRelevant` 也排除了另一域 pass（`src/App.tsx:397-400,541-548,2794-2810`）。

**confirmed** — Runtime 编译 Sound 时把共享源码区间错误标成 `pass: 'common'`（`src/shadertoy/runtime.ts:844-846,1051-1053`），但 App 的 Sound-only Graph 和 code 路径只保存 `origin.pass === 'sound'` 的 Runtime diagnostics（`src/App.tsx:851-852,1076-1086`）。例如 Common 引用只由 Image 源码提供的 helper 时，Visual 可保持 LKG；启用或修改 Sound 会让 Sound candidate 在 Common 区间失败。`soundCompileState` 最后仍变成 `ready`，successful Sound revision 不更新但错误计数为零，因此 Sound 状态栏显示“编译通过”，仅导出门禁通过 revision mismatch 阻止 WAV。

诊断需要携带产生它的 Runtime lane，或在 requested Sound 域中保留 `common` origin；双域请求可把共享错误投影到两个 lane。应增加 Sound-only Common 编译失败测试，断言状态栏、diagnostics 与 successful revision 一致。

## Sound snapshot 与 Graph acceptance 证明

`verify-m6` 断言 rejected Sound 后继续使用旧 sampler 的 nearest/clamp 配置，并在异步 `renderAudio` 中途提交新 Sound candidate：旧 program/texture 在 promise 完成前未删除，完成后进入 deleted 集合（`scripts/verify-m6.mjs:724-777`）。该 verifier 本轮通过，上一报告的生命周期证明缺口已关闭。

Visual candidates 仍以全部启用视觉 Graph 为一个集合，只有 compiler、拓扑、uniform contract 与 Runtime `visualOk` 全部成立才调用一次 `acceptGraphCohort`；Sound 使用独立 cohort。successful lane revision 只在相应 accepted 结果后写入，并在 Runtime 返回后复验全局 request revision（`src/App.tsx:837-866,1039-1047`）。未发现错误 successful revision 或 Visual cohort 部分提升。
