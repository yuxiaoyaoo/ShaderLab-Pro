# M5 多 Pass Graph、原子 cohort 与隔离式 Runtime 历史

本次 M5 将 Pass 内节点图与项目级 Pass Graph 拆成独立文档，以 resolved Pass Graph 驱动 Graph 编译环境、Runtime 拓扑和持久化，并把多 Pass Graph artifact 作为一个 Runtime cohort 接受。Runtime 使用显式 current/previous timing 与独立 capture buffer，项目保存通过批量原子写入把 `shaderlab.json` 放在最后提交。自动验证全部通过，但 App 状态流仍有导出门控缺口，旧项目也会在首次保存时丢失部分 channel 数据。

Watch for: **confirmed** — 旧 1.x/2.0 项目的非 buffer channels 会在首次保存时被清空，无法表示的 feedback 也会被静默移除；**confirmed** — 有效 Pass Graph 编辑后的 debounce 窗口仍可签发与旧 Runtime cohort 混合的导出票据；**confirmed** — Code endpoint 与物理 slot 可不一致且仍通过解析；**confirmed** — Pass Graph 无效时仍可直接导出 Graph JSON。

**Verdict**: NEEDS_CHANGES

## High-level view

Pass 内 `GraphDocument` 只保存节点表达式，项目级 `PassGraphDocument` 单独保存 pass 连接、slot 和帧时序，编译器只接收 resolved channel environment。边界本身清晰，但 **confirmed**：Code endpoint 和 resolved slot 缺少一致性约束，UI 所指的 `iChannelN` 可与 Runtime 实际绑定位置分叉。

候选 artifact 只进入候选 Runtime setup，`effectiveSources` 只叠加 `runtimeAcceptedArtifact`；多 Graph pass 在一次 Runtime compile 成功后统一提升。保存会按当前文档和 Pass Graph 环境重编译核验 artifact，原子批次也把 graph、fallback GLSL 和 Pass Graph 放在 meta 之前。

Pass Graph 无效时编译入口不调用 Runtime，项目保存及 ticket 保护的导出失败，旧预览得以保留。不过 **confirmed**：Graph JSON 导出绕过该门控；**confirmed**：合法 Pass Graph 变更只在 300ms debounce 到期时推进 Runtime revision，窗口内视觉导出会把新 Pass Graph identity 与旧 Runtime/effective cohort 组合成有效 ticket。

旧项目先把 legacy channels/feedback 投影为 Pass Graph，再在保存时从 resolved graph 反向覆盖元数据。**confirmed**：投影只容纳 buffer channel，feedback 在无空 slot 时也没有失败信号，保存随后无条件清除原字段。

Runtime 的 buffer 执行顺序来自显式拓扑，current/previous 选择不依赖数组顺序；capture 使用独立 ping-pong buffers 并在结束后恢复 preview buffers。代码追踪未发现这两项不变量的新增违例。

1. **旧项目 channel/feedback 数据丢失（confirmed）** — 非 buffer channels 和无法分配 slot 的 feedback 不进入 Pass Graph，首次保存仍会清空原字段；迁移必须完整保留，或在无法无损表示时拒绝保存。

## 旧项目首次保存会删除无法投影的 channels 与 feedback

`normalizeChannels` 会保留旧项目中的 `texture`、`keyboard`、`volume` 和 `buffer` channel，但 `passGraphFromLegacy` 在 `src/project/passGraph.ts:241` 跳过所有非 buffer channel。`saveProjectTo` 随后在 `src/project/projectIO.ts:98-110` 用 `legacyChannelsFromPassGraph` 覆盖每个 Image/Buffer pass 的完整 `channels`，并无条件写入 `feedback: undefined`。可正常加载的 1.x 或既有 2.0 项目只要保存一次，未进入 Pass Graph 的 channel 配置就永久从 `shaderlab.json` 消失；这是 **confirmed** 的迁移数据丢失。

`passGraphFromLegacy` 也只在找到空 slot 时创建 feedback self-edge（`src/project/passGraph.ts:253-260`）。四个 slot 均被占用且没有显式 self channel 时，它既不报错也不保留 legacy 标记，保存阶段仍清除 `feedback`；这是 **confirmed** 的不可逆正规化。M5 脚本仅覆盖一个 buffer channel 加一个可分配 feedback slot，没有覆盖非 buffer channel 或满四槽 feedback。

## Pass Graph debounce 可签发混合新旧 cohort 的 ExportTicket

`updatePassGraph` 在 `src/App.tsx:911-915` 立即替换 Pass Graph，却只调用 `scheduleGraphCompile()`；timeout 执行前不会增加 `runtimeSetupRevision`，也不会把 Graph editor 标成 stale。约 300ms 内，`currentExportInput`（`src/App.tsx:457-478`）仍看到旧 successful Runtime revision 和 `ready` artifact，却读取新的 `passGraphResolution().revision`。只要新图本身有效，`exportEligibility` 就会签发 ticket，视觉导出可针对仍运行旧 setup 的 Runtime 开始 capture；这是 **confirmed** 的 identity/cohort 不一致。

纯 Code 项目同样有该窗口，且 Code ticket 不携带 `passGraphRevision` 或 `effectiveSourcesHash`。Pass Graph 提交应立即使旧 Runtime/ticket 失效；debounce 只能延迟重编译，不能延迟失效。

## Code endpoint 与 Runtime slot 可分叉

面板在 `src/components/ProjectPassGraphPanel.tsx:69-74` 允许独立修改 Code `endpoint.slot` 和分配字段 `slot`；`resolvePassGraph` 只用前者做 endpoint 去重、只用后者做实际分配，并未要求相等。`{ endpoint: code-slot 1, slot: manual 2 }` 或 `{ endpoint: code-slot 2, slot: auto }` 因而能通过校验，但 Runtime 与持久化 projection 按 resolved slot 绑定纹理，GLSL 引用的 `iChannel1` 得不到该连接；这是 **confirmed** 的有效性漏检。

该状态会让界面、Runtime 和保存结果表达不同目标。Code endpoint 应直接决定物理 slot并禁止 auto/不同 manual slot，或 schema 应删除重复字段；修复前必须把该组合判为无效并走既有 fail-closed 路径。

## 无效 Pass Graph 仍允许 Graph JSON 导出

`exportGraphJson` 在 `src/App.tsx:1269-1278` 直接序列化当前/恢复 Graph 文档并写文件，不检查 Pass Graph diagnostics、compile status、accepted cohort 或 ticket。因此 Pass Graph 无效时该入口仍成功；相对于“Pass Graph 无效阻止保存/导出”的要求，这是 **confirmed** 的旁路。

如果 Graph JSON 的产品语义是紧急 authoring 备份，应明确改名和标注，并显式从该不变量中排除；按当前“导出”入口，它应复用统一门控。
