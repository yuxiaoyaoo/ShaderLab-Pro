# M5 recovery cohort 激活与真实 WebGL 执行回归

第三轮改动补上了 identity mismatch 后的恢复规划器，并把 WebGL 回归从纯 helper 推进到真实 `ShadertoyRuntime` 公共 API。合法的全 recovery cohort 现在能重新进入 editor、触发统一 Runtime compile，并在 accepted 后恢复 enabled Graph 的保存与导出；两帧 preview 的 current/previous、统一 flip、sampler/unit、目标尺寸 capture 隔离和取消恢复也已有 executor 级观测。恢复闭环仍不完整：planner 用全部文档做 topology resolve，却只重新编译 recovery 文档；disabled Graph 又被保存契约要求拥有永远不会生成的 Runtime artifact。恢复文档没有结构化原因，且 capture executor 只跑 frame 0，分别留下错误重激活和连续导出 history 的缺口。

Watch for: **[高][confirmed]** mixed editor/recovery cohort 中，candidate 可让现有 dirty editor 在新 environment 下失效，但 planner 仍提升 recovery 并清除 identity issue；**[高][confirmed]** disabled Graph editor 不进入 Runtime cohort，却被 `currentGraphSaveOptions` 要求 Runtime accepted，项目无法保存；**[中][confirmed]** 任意 Pass Graph 编辑都会重激活 runtime-rejected recovery，原因和诊断在 Runtime 再拒绝前丢失；**[中][confirmed]** fake WebGL 只执行一次 `captureAt(... frameIndex=0)`，没有验证 capture frame 0→1 的 feedback 连续性。

**Verdict**: NEEDS_CHANGES

## High-level view

`planPassGraphIdentityRecovery` 以 candidate 和 recovery/editor 合并后的 documents 解析同一个 Pass Graph revision，任一 recovery Graph 编译失败时会阻止全部 recovery promotion。**[高][confirmed]** 它没有在该 revision 下分类 editor documents；`updatePassGraph` 因而可能保留一个在新 channel environment 下已经无效的 dirty editor，同时激活 recovery、清除 identity issue，直到异步 cohort compile 才暴露失败。

`updatePassGraph` 的成功分支保留既有 editor 的 document、history、selection、generation 和 accepted artifact，只把状态置为 pending；失败分支不删除 recovery 或清 issue。**[高][confirmed]** promoted disabled Graph 也被置为 pending，而 cohort 只编译 enabled Graph；保存遍历全部 Graph authoring pass，导致 disabled state 永远拿不到它被要求提供的 Runtime artifact。

Recovery storage 只有 document 和 diagnostics，没有 identity/compiler/runtime 等结构化 reason。**[中][confirmed]** planner 在每次 Pass Graph 编辑时都会尝试所有 recovery documents，所以首次 Runtime reject 后的只读 Graph 会被重新暴露为 editor、清空 runtime recovery diagnostics，再由下一次 Runtime compile 决定是否退回只读；Runtime acceptance 仍 fail closed，但 UI 状态和错误归因会短暂失真。

fake WebGL harness 确实经过 `ShadertoyRuntime.compile`、两次 `probePixel`、`captureAt` 和 `endCapture`，并从独立记录的 framebuffer attachment、texture/sampler unit 与 texture label 检查真实 binder/flip wiring。**[中][confirmed]** capture 只执行 frame 0；frame 1 是否复用同一 capture ping-pong set、previous 是否读取 capture frame 0，仍由纯 `captureFrameNeedsReset` 断言间接推断。

Candidate 与 accepted artifact 仍隔离，`effectiveSources` 只采用 Runtime accepted cohort；旧 M3 migration、Code↔Graph resolved slot、多边/满槽、原子保存与 autosave identity、export ticket、preview freeze 和 native-size capture 的既有断言均继续通过。

## Recovery planner 没有分类同一 revision 下的现有 editor

`planPassGraphIdentityRecovery` 先用 `{ ...recoveryDocuments, ...editorDocuments }` 调用 `resolvePassGraph`，但随后只遍历 `Object.keys(recoveryDocuments)` 调用 `classifyPersistedGraph`（`src/state/graphRecovery.ts:62-76`）。因此它证明的是“全部 recovery documents 在新 environment 下可编译”，不是“当前 recovery/editor cohort 在同一 revision 下可编译”。

这是 **[高][confirmed]** 的原子恢复缺口。复现场景：Image 已有带未保存 history 的 editor，并通过 `input.channel-sample` 使用当前 Pass Graph endpoint；Buffer A 处于 identity recovery。编辑 candidate，在修复 reference identity 的同时删除 Image endpoint。resolver 只校验存在的 edge，不要求每个 sample node 都有 edge，因此 candidate 可 resolve；Buffer A recovery 可通过 classification，plan 返回 `promote`。`updatePassGraph` 随即创建 Buffer A editor、保留 Image history、清除 `pass-graph.invalid/reference-*` issue 并安排 cohort（`src/App.tsx:963-1017`），之后 Image compiler 才因 `Channel sample ... is not connected` 失败。结果是 recovery 已被部分激活、identity issue 已消失，但 save/export 仍 blocked。

应在 resolved candidate 的同一 `channelEnvironmentRevision` 下 classification 所有 current editor 和 recovery documents；任何一个失败时返回 blocked，只更新 candidate/dirty，并保留 recovery、editor 和原 issue。成功时只创建 recovery editors，既有 dirty editor/history 按当前实现原样保留。测试需覆盖 mixed dirty editor + recovery、invalid candidate、invalid recovery 和 valid promotion，并断言 issue map、history/generation 与激活集合。

## Disabled Graph 永远无法满足保存门控

Runtime cohort 定义为 enabled Graph passes（`src/App.tsx:463,573`），但 identity promotion 把所有 recovery editors——包括 disabled pass——置为 pending（`src/App.tsx:989-997`）。disabled editor 不会经过 `compileGraphCohort`，因此没有 `runtimeAcceptedArtifact`；`currentGraphSaveOptions` 却遍历所有 authoring kind 为 Graph 的 pass 并要求 `graphCanExport`（`src/App.tsx:1219-1227`）。

这是 **[高][confirmed]** 的持久化阻塞。复现方式：项目含 disabled Buffer A Graph，打开 identity mismatch 项目并修复 Pass Graph，或直接打开 identity-valid 项目。Image/其他 enabled cohort 可 Runtime accepted，视觉导出也只看 enabled Graph 而恢复；保存仍报 “bufferA Graph 尚未被同一 Runtime cohort 接受或处于 stale”。即使项目只有 Code Image 和一个 disabled Graph，空 Graph cohort 成功编译 Code runtime 后也不会给 disabled editor artifact。

需要明确 disabled Graph 的持久化契约：要么 graph-compile 后保存其 artifact 而不要求 Runtime acceptance，要么保存时保留其已持久化 fallback/identity；不能让只参与 authoring persistence 的 pass 依赖 enabled Runtime cohort。增加 disabled Graph 的 open→identity recovery→save→reopen 测试，并验证重新 enable 后才进入 Runtime acceptance。

## Recovery reason 混用导致 runtime-rejected 文档被无条件重试

`activateReadOnlyGraphRecovery` 对 identity mismatch、Graph compile failure 和首次 Runtime rejection 都写入同一个 `graphRecoveryDocuments` map（`src/App.tsx:550-557,640-647`）。`planPassGraphIdentityRecovery` 不接收 reason，`updatePassGraph` 也不要求当前存在 identity issue；只要 document 在新 Pass Graph environment 下通过 Graph compiler，就会创建 editor、删除 recovery diagnostics 并设置 `loadedGraphPendingRuntimeRecovery=true`（`src/App.tsx:963-1013`）。

这是 **[中][confirmed]** 的状态归因错误。复现场景：打开一个 Graph compiler 成功但 Runtime shader compile/link 失败的 persisted project，等待它进入 `graph.runtime-rejected-recovery`；只修改一条无关 edge 的 filter/wrap。Graph 会立即从“只读 generated GLSL recovery”变为 editable，Runtime 错误消失至少一个 debounce 周期；若 Runtime 仍拒绝才再次回到 recovery。坏 shader 不会进入 `effectiveSources`，但 readonly 边界和诊断不稳定。

应给 recovery entry 记录 `identity-mismatch | compiler-invalid | runtime-rejected | missing/unsupported` 等 reason。identity repair 只自动 promotion identity-bound entries；如果 Pass Graph 变化被允许重新验证 runtime-rejected entry，应保留原诊断到新 Runtime acceptance，并将该状态明确建模为 revalidation。

## Executor harness 已覆盖 preview wiring，但没有连续 capture frame

测试实例化真实 `ShadertoyRuntime`，通过公开 `compile` 装载两个 Buffer 和 Image，再用两次 `probePixel` 观察真实 `draw`、buffer attachment、全局 flip 后 Image binding、四个 sampler uniform、空 slot dummy texture，以及 linear/repeat 与 nearest/clamp sampler（`scripts/verify-m5.mjs:295-370`）。fake 的输出 label 来自当前 GL binding state，不调用 `selectChannelTexture`，所以错误的 unit、attachment、两帧 flip 或 previous index 会改变记录并让断言失败；这关闭了第二轮“只复刻 helper 公式”的主体问题。

目标尺寸路径真实调用 `captureAt(0, 0, ..., { width: 640, height: 360 })`，验证 capture 使用四张独立 texture、两个独立 framebuffer、不采样 preview texture，并在 `endCapture` 后删除 capture 资源、保留 preview ping-pong 和恢复暂停前 history（`scripts/verify-m5.mjs:373-417`）。**[中][confirmed]** 但只有 frame 0 被执行。一个每次 `captureAt` 都错误 reset feedback、重新建 buffer，或 frame 1 previous 仍读 clear texture 的实现仍可通过；当前唯一“forward frame 不 reset”的检查是纯 helper（`scripts/verify-m5.mjs:268-271`）。增加同一 capture session 的 frame 0、frame 1 两次调用，断言不重新分配 capture texture，第二帧 attachment flip，Buffer/Image previous label 来自 capture frame 0，再执行 `endCapture` 检查 preview history。
