# M3 Shader Graph 持久化、恢复与导出门控

这组改动把 Graph v1 接入项目 2.0：GraphDocument 成为 Image Graph 的可编辑源，只有经过 Graph 编译且被 Runtime 接受的 artifact 才能保存、Detach 或导出。项目保存改为 Graph JSON、generated GLSL、其余 Pass 和最终 `shaderlab.json` 的同批次提交，Autosave V2 同时保留 meta、effective sources、Uniform 和 Graph 文档。missing、JSON corrupt、future-version 与 hash mismatch 的主要恢复路径已经建立，Graph 模板、1.0 Code 迁移和现有验证均保持通过。阻塞点在于 schema 合法但 Graph 编译失败或 Runtime 拒绝时没有启用持久化 fallback；项目层还接受 App 尚未协调的 Buffer Graph。

Watch for: **confirmed** — 编译级无效或 Runtime 拒绝的持久化 Graph 会显示 stale，却不会加载项目内 generated GLSL fallback，预览可能继续显示上一个项目；**confirmed** — Buffer Graph 可被项目层加载，但不会进入 App 的 Graph 协调，保存会失败且导出不会被冻结；**confirmed** — 原子批次已经提交成功后，backup 清理失败仍被上报为“保存失败”。

**Verdict**: NEEDS_CHANGES

## High-level view

Graph 保存契约收敛在 `validateGraphSave` 与 `runtimeAcceptedArtifact`：当前文档会被重新规范化和编译，source、sourceHash 与 semantic revision 必须完全一致。布局变化不改变 revision；语义变化则在 Runtime 接受前冻结保存和导出。

项目打开只在 `parseProjectGraph` 不返回文档时进入只读 fallback。schema 通过但结构、类型或 Runtime 编译失败的 Graph 仍会激活编辑状态，导致项目保存的 generated GLSL 以及 Autosave 中的 accepted effective source 无法承担恢复职责。

持久化层按 `image + bufferA-D` 处理 Graph，UI、effective sources、accepted artifact、Autosave 恢复和导出判断却只有 Image 状态。M5 之前若不拒绝 Buffer Graph，文件格式承诺会宽于 App 的实际保存和安全导出能力。

原生批量写入先 staging 再按序替换，失败时逆序恢复，`shaderlab.json` 最后提交。提交后 backup 清理仍被计入成败，且真实多文件 Windows 中途失败没有故障注入覆盖。

## Accepted artifact 是 Graph 保存与导出的唯一语义门

`src/project/graphIO.ts::validateGraphSave` 会验证 artifact.source 的确定性 hash，重新编译规范化后的 Graph，再比较 sourceHash、revision 和完整 source。`src/App.tsx::currentGraphSaveOptions` 只提交 `graphCanExport` 为真的 `runtimeAcceptedArtifact`，因此仅通过 Graph compiler、但被 WebGL Runtime 拒绝的候选不能落盘，stale Graph 也不能借用旧 artifact 冒充当前 revision。

`effectiveSources` 只有在 accepted artifact 存在时才覆盖 Code source，Graph 保存又直接写 validated artifact。布局命令不增加 generation，重新编译仍得到相同 revision，因此节点位置和 viewport 可以随同 accepted 语义保存。

## 编译级无效 Graph 绕过 generated GLSL fallback

**High — confirmed.** `src/project/graphIO.ts::parseProjectGraph` 只运行 schema normalization；缺 Fragment Output、循环、未知节点或类型错误仍可能返回 `document`。`inspectPersistedGraph` 在 `compileGraph(document)` 失败时不产生 issue，`src/project/projectIO.ts::openProjectFrom` 随即把文档放进 `graphDocuments`。实测删除默认图 Fragment Output 后，parse 仍返回文档且无 issue。

`src/App.tsx::graphFallbackActive` 只识别 `authoring.kind === "graph" && !graphEditor()`。上述文档会被 `activateImageGraph` 激活，`compileGraphGeneration` 失败后直接返回；Graph 编译成功但 Runtime 拒绝时也只有 stale 状态，没有 persisted fallback 对应的 accepted artifact。`generatedCodeSelection` 不再选择 `sources.image`，Detach fallback 不可用，Runtime 也没有编译当前项目保存的 generated GLSL。此前打开过其他项目时，预览可能继续显示旧项目的最后成功画面，而状态栏只说“预览保持上次有效版本”。

`doRecover` 同样只检查 parse 是否返回文档，所以 schema-valid 但不可编译的 Autosave Graph 会隐藏随快照保存的 accepted effective GLSL。修复应区分 schema-valid、Graph-compile-valid 与 Runtime-accepted：Graph 编译失败时记录节点级 issue，并以 recovery 状态保留原文档但运行/显示 persisted fallback；首次 Runtime 接受失败时也尝试 fallback，成功后明确标记只读恢复并允许显式 Detach to Code。

## Buffer Graph 被项目格式接受，却没有进入 App 的 Graph 协调

**Medium — confirmed.** `src/graph/schema.ts::PASSES` 和 `src/project/projectIO.ts::GRAPH_PASS_IDS` 接受 `bufferA-D`，打开和保存也收集这些 document/artifact。App 只有 `imageAuthoring`、单个 `graphEditor`、`opened.graphDocuments.image` 和 `{ image: ... }` save options；effective sources 也只注入 accepted Image source。

当前 schema 合法的 Buffer Graph 因此会以普通 Code Buffer 展示 generated fallback，允许用户编辑，却在保存时因缺少 Buffer accepted artifact 拒绝整个项目。`canExportCurrent` 也只检查 Image，Buffer Graph missing、invalid、stale 或从未被 Runtime 接受时仍可导出磁盘 fallback。M5 前应在 migration/open boundary 拒绝或只读隔离非 Image Graph；若 M3 要提前承诺 Buffer 持久化，则 document/artifact/status、effective sources、Autosave、save options 和 export gate 都必须改为按 Pass 协调。

`src/project/migrations.ts::normalizeAuthoring` 还未依据 Pass ID 限制 graph authoring，Common/Sound 可以保留一个项目 I/O 永远不读取的 graphFile 标记。允许集合应与当前产品能力一致。

## Windows 批次提交的成功边界

`src/project/projectIO.ts::saveProjectTo` 把 Graph JSON、artifact GLSL、Code Pass 和最后的 `shaderlab.json` 放入同一批次。原生端在同目录写 temp 并 `sync_all`，提交失败时逆序恢复；Graph path 拒绝 traversal，JS/Rust 两端拒绝 Windows 大小写别名目标，恢复失败则保留 backup。

**Medium — confirmed.** `src-tauri/src/lib.rs::write_text_files_atomic` 在全部目标替换后，若任一 `.bak` 无法删除便返回 `Err("文件已提交，但无法清理 backup")`。磁盘此时已经是新 Graph/GLSL/meta，App 却显示保存失败、不采用 normalized meta 并保持 dirty；Autosave 也忽略已经写入的快照。提交完成后的 cleanup 应降为 warning，或返回结构化 committed 状态，不能进入普通失败/重试语义。

**Low — confirmed.** `atomic_write_tests` 直接验证单文件 `rollback_atomic_files`，`scripts/verify-m3.mjs` 则用一次性写 Map 的 mock 检查顺序和重复路径，没有让真实批次在第二或后续 rename 时失败。应通过可故障注入的文件系统适配层覆盖已有/新文件混合、Graph 已提交后 GLSL/meta 失败、当前 backup 已建立但 temp rename 失败，以及回滚失败保留 backup。

## 验证范围与未覆盖恢复路径

`npm run typecheck`、`verify:m0`、`verify:m1`、`verify:m2`、`verify:m3`、`npm run build` 和 `cargo test --lib` 全部通过。现有 M3 checks 覆盖 1.0 Code migration、Graph round trip、missing/corrupt/future/hash mismatch、accepted artifact 拒绝、Autosave V2 时间选择和批次顺序；内置 Graph 模板在模块加载和应用时编译，Image Graph stale/pending 的媒体、`.frag` 与 Shadertoy 导出入口也有统一门控。

**Not tested — confirmed:** compiler-invalid persisted Graph/Autosave fallback、首次 Runtime 拒绝后的 persisted fallback、Buffer Graph 的 App/save/export 行为，以及真实多文件 Windows 中途提交失败。补齐这些行为测试后，旧 Code 工作流仍应继续运行 M0–M3 与生产构建作为回归门。
